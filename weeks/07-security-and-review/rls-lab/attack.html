Only test a project you own.

This page connects to a Supabase project with its publishable key and tries ordinary reads and writes, so you can see what any stranger with that key could do. Use it only on a project you created: the practice table from setup.sql, or your own capstone's tables. Pointing it at a database you don't own is not part of this course and may be illegal.

Your URL and key stay in this tab's memory only. Nothing is saved, and nothing is sent anywhere except to the Supabase project you name. Close the tab and they're gone.

1. Connect to your project

In the Supabase dashboard, click Connect at the top, or go to Settings → API Keys. Copy the Project URL and the publishable key (it starts with sb_publishable_). Never paste a secret key (sb_secret_…, or the old service_role key) into any web page: this page refuses them.

How to read the results
  • ALLOWED The publishable key could do it. Fine for things a stranger should do (read public rows, add a guestbook message); a leak for anything else.
  • 0 ROWS (FILTERED) No error, but no rows came back or changed. With RLS on, rows you may not see or change are invisible, so the request matches nothing. That is RLS working, as long as the table really has rows (check the Table Editor).
  • REFUSED BY RLS A policy's with check rule rejected the new row: "new row violates row-level security policy".
  • REFUSED: NO GRANT "permission denied": the role has no permission for this action on this table at all. That blocks it, but through a grant, not RLS. From 30 October 2026 new tables get no grants until you add them. When you add one, turn RLS on and add policies in the same script; never fix this with a grant alone.
  • REFUSED BY A COLUMN RULE The data itself broke a column rule (empty, too long, wrong type). Valid data might still get through, so this says nothing about who may write.
  • ERROR Not a security result: a wrong URL, key, table or column name, or the project is paused. Fix the setup and try again.
